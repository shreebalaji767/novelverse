# NovelVerse

**NovelVerse** is a free, responsive light-novel reading and publishing platform hosted on GitHub Pages.

- **Live website:** https://shreebalaji767.github.io/novelverse/
- **Repository:** https://github.com/shreebalaji767/novelverse
- **Publishing branch:** `main`

NovelVerse is deliberately a static website. It uses HTML, CSS and vanilla JavaScript, with public content stored as files in this repository and personal reading data stored locally in the reader's browser.

**The Wrong Heiress:** 58 published chapters.

## Project principles and architecture

| Need | Implementation |
|---|---|
| Website and interface | HTML, CSS and vanilla JavaScript |
| Public novel catalogue and series metadata | JSON files committed to this repository |
| Chapter text | Markdown, HTML or text files committed to this repository |
| Character profiles and world lore | JSON files committed to this repository |
| Release dates and announcements | JSON files committed to this repository |
| My Library, bookmarks and reading progress | Browser `localStorage` |
| Offline app shell | Service Worker and Cache API |
| Personal-data portability | User-controlled JSON export and import |
| Publishing and deployment | Manual Git commits to `main`, deployed by GitHub Pages |

**Do not add** a database, backend, server-side functions, hosted personal-data storage, account/authentication system, paid API, subscription, advertisement network or other paid service. Keep the project compatible with free static GitHub Pages hosting.

Personal data remains in the browser profile on the device where it was created. It does not automatically synchronize across browsers or devices and is not uploaded to GitHub. Readers can export a backup and import it on another device themselves.

## Site navigation and pages

The shared navigation is generated by `js/core/site.js` on pages with the `.site-header` header. It keeps the same destinations and active-page indication throughout the site, including detail pages. The responsive menu is controlled by the shared script.

| Page | File | Purpose |
|---|---|---|
| Home | `index.html` | Landing page and featured published series |
| Novels | `novels.html` | Public catalogue, search and status filtering |
| Series details | `series.html?id=<series-id>` | Series information, volumes, chapters, characters and world overview |
| Reader | `reader.html` | Chapter reading room and reading controls |
| Characters | `characters.html` | Searchable, series-filtered character directory |
| Character profile | `character.html?id=<character-id>` | Individual character information |
| Worlds | `worlds.html` | Searchable, series-filtered world directory |
| World profile | `world.html?id=<world-id>` | Individual world information |
| My Library | `my-library.html` | Personal, browser-local saved shelf and backup tools |
| Release calendar | `calendar.html` | Published release announcements and dates |
| Publishing Studio | `publish.html` | Local authoring, validation and package export |
| About | `about.html` | Platform principles, reading experience, privacy and publishing model |

`library.html` is a legacy route retained for compatibility; the personal shelf is named **My Library**. The public catalogue is always called **Novels**, never Library.

### Branding, responsive layout and installation

- The NovelVerse emblem is used for both the visible brand mark and the favicon, with a transparent background.
- Shared responsive styles adapt the layout and navigation to desktop, tablet and mobile screens.
- The web app manifest and service worker provide an installable app experience where supported by the browser.
- The **Install app** control uses the browser's native install prompt when available and provides manual installation guidance otherwise. Installation availability and prompts depend on the browser and platform.
- The service worker caches the static app shell for offline access after it has been installed and cached successfully. Availability of individual chapter content offline depends on whether that content has previously been fetched and cached.

## Reading experience

The Reader supports:

- Adjustable text size and reading-column width.
- Dark, light and sepia reading themes.
- Bookmarks.
- Saved reading position and chapter progress.
- Previous and next chapter navigation.
- Local persistence of reader preferences and progress.

Reader settings and progress use the `novelverse.reader.v1` browser storage key. The reader loads chapter files referenced by the public catalogue; it does not require an account.

## My Library and personal backups

**My Library** is a personal shelf stored on the current device, separate from the public Novels catalogue. Reading a novel or opening a chapter never adds it to My Library automatically. Readers must choose **Save** or **Add to My Library** themselves from a novel card or series page.

Current tools include:

- Add and remove saved series.
- Search the saved shelf.
- Reading statistics.
- Export a JSON backup.
- Import a backup with validation and merge behavior, preserving existing local data rather than replacing it.
- Clear saved novels.

The backup includes supported saved-series and reader data such as preferences, bookmarks and reading positions. Keep backup files somewhere safe. Import a backup only when you trust its source.

Storage keys currently include:

- `novelverse.myLibrary.v1` — saved series.
- `novelverse.reader.v1` — reader preferences, bookmarks and progress.

Browser storage can be cleared by the user, browser settings or device cleanup. Export backups periodically if the data matters to you.

## Character and world encyclopedias

The public encyclopedia is driven by committed JSON files:

- `data/characters.json` — character profiles, aliases, appearance, personality, history, abilities, affiliations, relationships and chapter appearances.
- `data/worlds.json` — world settings, geography, history, locations, organizations/factions and chronological events.

Each character record requires a stable `id`, its parent `novelId`, and a `name`. Optional fields can include `role`, `summary`, `aliases`, `appearance`, `personality`, `history`, `abilities`, `affiliations`, `relationships` and `appearances`. Relationship references point to character IDs within the same series; appearance records may reference chapter IDs.

Each world record requires a stable `id`, its parent `novelId`, and a `name`. Optional fields include `type`, `summary`, `geography`, `history`, `locations`, `organizations` and `timeline`. Location, organization and timeline entries require stable IDs and a `name` or `title`. Timeline entries may reference chapter IDs.

Use `spoiler: true` on supported records or entries to hide those details until a reader enables spoiler reveal. This is a reader convenience, not access control; all committed JSON is public and can be inspected directly.

## Publishing Studio

Open `publish.html` to prepare a series package in the browser. The Studio supports:

- Series metadata, including ID, title, author, status, synopsis, genres and tags.
- Volumes and chapter entries.
- Markdown chapter text.
- Optional character and world JSON input.
- Pre-flight validation.
- Local draft saving and draft/package import.
- Exporting a JSON publishing package with chapter file paths and contents.

The Studio's local draft storage key is `novelverse.publisherDraft.v1`. Drafts remain in the current browser until exported. The Studio does **not** upload files, access GitHub, commit changes or deploy the site. Never enter GitHub passwords, tokens or other credentials into it.

### Manual publishing workflow

1. Open Publishing Studio and prepare your own content.
2. Validate the package and export its JSON file.
3. Review the exported package and keep a backup.
4. Add chapter files under `novels/<series-id>/chapters/` using the paths in the package.
5. Merge the series entry into `data/novels.json`; merge any character and world entries into `data/characters.json` and `data/worlds.json`.
6. Preserve all existing catalogue entries. **Merge** new entries; do not replace the existing catalogue with a one-series export.
7. Run the local validation checks described below.
8. Commit the changes to `main`. GitHub Actions validates the repository and deploys the static site to GitHub Pages.
9. After the workflow succeeds, verify the published series on the live Novels page.

## Content data files

| File | Contents |
|---|---|
| `data/site.json` | Site-level content and configuration |
| `data/novels.json` | Public novel and series catalogue |
| `data/chapters.json` | Chapter index |
| `data/characters.json` | Character encyclopedia records |
| `data/worlds.json` | World encyclopedia records |
| `data/releases.json` | Release calendar data |
| `data/announcements.json` | Public announcements |

A series entry should use a stable unique `id`, `title`, `synopsis`, and supported optional metadata such as `subtitle`, `author`, `status`, `genres`, `tags`, `updatedAt` and ordered `volumes`.

Each volume should have a stable `id`, `title`, optional `order`, and a `chapters` array. Each chapter should have a stable `id`, `title`, safe repository-relative `path`, and optional `order` and `subtitle`. Check the current catalogue and validation script for the exact accepted structure before adding content.

## Local development and validation

Serve the repository over HTTP because the website loads JSON files with `fetch`. From the repository root, run:

```sh
python -m http.server 8000
```

Then open http://localhost:8000/ in your browser.

Before committing, run:

```sh
node tests/validate-data.mjs
for file in js/core/*.js js/pages/*.js; do node --check "$file"; done
```

The validation script checks catalogue structure, unique IDs, safe chapter paths, chapter file references, character/world relationships and references, required pages and key site features. JavaScript files are syntax-checked by the deployment workflow as well.

## Deployment

The workflow in `.github/workflows/pages.yml` runs on pushes to `main` and can also be started manually through GitHub Actions. It:

1. Checks out the repository.
2. Runs `node tests/validate-data.mjs`.
3. Runs Node.js syntax checks on the core and page scripts.
4. Builds and deploys the repository contents to GitHub Pages.

A successful commit does not by itself mean the live site has updated. Check the GitHub Actions run and confirm the Pages deployment has completed.

## Contribution rules

- Keep the project free and static: HTML, CSS, vanilla JavaScript and repository-hosted content files.
- Preserve existing features, catalogue entries and user data formats when making changes.
- Do not invent or add novels, chapters, characters, settings or lore without supplied content and explicit approval.
- Keep public discovery under **Novels** and personal saved content under **My Library**.
- Keep shared navigation, responsive behavior, accessibility and offline caching consistent across pages.
- Do not introduce paid services, ads, accounts, databases, backends or external API dependencies.
- Validate changes and confirm the GitHub Pages workflow before reporting a deployment as successful.
